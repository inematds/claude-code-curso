1

🎯 MVP mindset

MVP nao e um produto ruim. E a menor versao que resolve o problema real de alguem. A armadilha classica: ficar polindo features que ninguem pediu enquanto o problema central continua sem solucao. Claude Code acelera a construcao, mas voce precisa saber o que construir.

Pergunte: "Se eu tivesse apenas 1 tela e 1 acao, qual seria?" Essa resposta e o nucleo do seu MVP. Todo o resto e backlog. Diga ao Claude Code: "cria o fluxo minimo pra [problema X]" e resista a tentacao de adicionar "so mais um campo".

Em 1 frase: MVP = resolver UM problema de verdade, nao dez pela metade.

2

🔪 Priorizacao ruthless

Toda feature que voce adiciona tem custo: codigo pra manter, bugs pra consertar, complexidade pra explicar. A priorizacao ruthless diz NAO pra 90% das ideias pra que os 10% restantes fiquem excelentes. Use a matriz impacto vs esforco: alto impacto + baixo esforco = faz agora. O resto espera.

priorizacao.md
## Matriz de Priorizacao

| Feature         | Impacto | Esforco | Decisao      |
|-----------------|---------|---------|--------------|
| Auth basico     | Alto    | Baixo   | MVP - faz    |
| Dashboard admin | Medio   | Alto    | v2 - espera  |
| Dark mode       | Baixo   | Baixo   | Nice-to-have |
| Notificacoes    | Alto    | Medio   | v1.1 - logo  |
| Multi-idioma    | Baixo   | Alto    | Backlog      |

Armadilha classica

"Mas e so mais uma feature!" Nao. Cada feature "pequena" acumula. 20 features "pequenas" = um produto confuso. Priorize impiedosamente.

Em 1 frase: priorizar = decidir o que NAO fazer para que o essencial fique excelente.

3

✅ Launch checklist

Antes de lancar, passe por esta checklist. Nao e sobre perfeicao. E sobre nao quebrar na frente do usuario. Claude Code ajuda: "audita esse projeto contra a launch checklist".

launch-checklist.md
## Pre-Launch Checklist

- [ ] README claro (o que faz, como instalar, como usar)
- [ ] .env.example com todas as variaveis documentadas
- [ ] Testes passando (pytest + CI verde)
- [ ] /health endpoint respondendo
- [ ] HTTPS configurado
- [ ] Secrets fora do repositorio (.gitignore)
- [ ] Backup do banco de dados
- [ ] Monitoring + alertas basicos
- [ ] Pagina de erro customizada (404, 500)
- [ ] Um usuario real testou antes de voce

Cada item tem um motivo. README confuso = ninguem adota. Secrets expostos = desastre. Um usuario real testando = bugs que voce nunca veria. A checklist nao e burocracia: e a rede de seguranca minima.

Em 1 frase: launch checklist = rede de seguranca contra os erros mais comuns de primeiro deploy.

4

🔄 Feedback loop

Lancou? Agora escute. O feedback loop e o motor de evolucao do produto. Metricas quantitativas (quem usou, onde dropou) + qualitativas (o que disseram, o que pediram). Sem feedback loop, voce esta codando no escuro.

Ferramentas minimas: analytics basico (Plausible, Umami), canal direto com usuarios (formulario, email, Discord/Telegram), e um lugar pra registrar o que ouviu (Notion, GitHub Issues, ate um .md no repo). O segredo: responder rapido. Um bug reportado e corrigido no mesmo dia vale mais que 10 features novas.

Em 1 frase: lance, escute, ajuste, repita. Sem loop de feedback voce esta adivinhando.

5

🔁 Iteracao pos-launch

O produto nao esta "pronto" no launch. Ele esta comecando. A iteracao pos-launch segue um ritmo: corrigir bugs criticos (dia 1-3), ajustar UX com base no feedback (semana 1-2), adicionar a feature mais pedida (semana 3-4). Micro-releases frequentes > mega-updates esporadicos.

Com Claude Code, o ciclo de iteracao encurta drasticamente. Bug reportado -> "corrige esse bug: [descricao]" -> testes -> deploy. O que levava dias agora leva horas. Use isso a seu favor: velocidade de resposta e uma vantagem competitiva real para projetos pequenos.

ritmo de iteracao
## Ciclo Pos-Launch

Dia 1-3:   Hotfixes (bugs criticos, crashes)
Semana 1:  Quick wins do feedback (UX, copy, fluxo)
Semana 2:  Refactor se necessario (divida tecnica)
Semana 3:  Feature #1 mais pedida
Semana 4:  Retrospectiva + planejar proximo ciclo

Regra: nunca fique mais de 2 semanas sem release.

Em 1 frase: releases pequenos e frequentes vencem mega-updates esporadicos.
