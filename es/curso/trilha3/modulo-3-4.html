1

🐘 PostgreSQL MCP

El PostgreSQL MCP conecta al agente con bases de datos Postgres mediante una connection string. Tools: query (ejecutar SQL), list_tables, describe_table. El agente puede analizar esquemas, generar informes, depurar datos e incluso sugerir índices.

La configuración pasa la connection string como variable de entorno: POSTGRES_URL=postgresql://user:pass@host:5432/db. Prefiere siempre el acceso de solo lectura para los entornos de producción.

settings.json (postgres)
"postgres": {
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-postgres"],
  "env": { "POSTGRES_URL": "postgresql://user:pass@localhost:5432/mydb" }
}

En 1 frase: MCP de PostgreSQL = el agente ejecuta consultas SQL en bases de datos PostgreSQL reales.

2

⚡ Redis MCP

El Redis MCP expone operaciones de caché y clave-valor: get, set, keys, ttl, del. Útil para depurar la caché, revisar colas y monitorear el estado de las aplicaciones en tiempo real.

Conexión mediante REDIS_URL: redis://localhost:6379. El agente puede inspeccionar claves, comprobar TTLs e incluso limpiar la caché cuando se lo pidas.

En 1 frase: Redis MCP = inspeccionar y operar cachés/colas de Redis mediante un agente.

3

🌐 HTTP/REST MCP

El HTTP MCP es un conector genérico para cualquier API REST. Configuras la URL base y los headers de auth, y el agente puede hacer GET, POST, PUT, DELETE en cualquier endpoint. Es la navaja suiza de los MCP.

Cada operación se convierte en una tool con parámetros para path, query params, headers y body. Ideal para conectar servicios internos que no tienen un MCP dedicado.

En 1 frase: HTTP MCP = conectar el agente a cualquier API REST con una configuración.

4

◈ GraphQL MCP

Si tu API es GraphQL, este MCP permite ejecutar queries y mutations directamente. El agente usa introspection para entender el schema y construir queries adecuadas automáticamente.

La configuración necesita el endpoint de GraphQL y, opcionalmente, headers de autenticación. El agente puede explorar el schema, listar types y ejecutar operaciones complejas con variables.

En 1 frase: GraphQL MCP = consultas y mutations GraphQL mediante el agente, con introspección del schema.

5

🔌 Conexión con servicios reales

Conectar MCPs a servicios locales es fácil. El desafío es conectar a entornos reales: staging, producción. Patrones comunes: túneles SSH para bases de datos remotas, configuraciones de entorno por proyecto (settings.json local frente a global) y connection pools para evitar la sobrecarga.

Regla de oro: nunca des acceso de escritura a producción mediante MCP sin supervisión. Usa read-only para consultas y análisis; write solo en staging o con un flujo de aprobación.

Nunca escribas directamente en prod

El agente puede ejecutar DELETE o DROP sin pensarlo dos veces. Los entornos de producción deben ser read-only mediante MCP. Escribe solo con aprobación o en staging.

En 1 frase: conectarse a staging/prod = túnel SSH + solo lectura + env por proyecto.

6

🔒 Seguridad de credenciales

Los MCP con acceso a DBs y APIs necesitan credenciales: connection strings, tokens, passwords. Estas credenciales quedan en settings.json o en variables de entorno. El riesgo: si se hace commit de settings.json en git, las credenciales quedan expuestas.

Best practices: (1) use env en settings.json en lugar de hardcode en los args, (2) agrega .claude/settings.json a .gitignore, (3) para equipos, usa un secret manager y referencia variables del shell.

.gitignore
# Nunca hagas commit de settings con credenciales
.claude/settings.json
.env
.env.local

En 1 frase: credenciales en variables de entorno + gitignore + secret manager = seguridad básica.
