📖 Glosario vivo

Términos clave de esta ruta. Vuelve aquí siempre que lo necesites.

MCP (Model Context Protocol) — protocolo abierto que permite a agentes de IA (como Claude Code) descubrir y usar herramientas externas de forma estandarizada, mediante JSON-RPC.
Tool — función que el MCP server expone al agente. Tiene nombre, descripción y un schema de entrada. Ej.: read_file, query_db.
Schema (inputSchema) — la descripción JSON Schema de los parámetros que acepta una tool. El agente la usa para saber qué enviar.
Protocolo — conjunto de reglas que define cómo se comunican dos programas. MCP usa JSON-RPC sobre stdio o HTTP.
Server — el proceso que expone tools mediante MCP. Puede ser un script de Node.js, un binario o un contenedor Docker.
Cliente — quien consume las tools del server. En nuestro caso, Claude Code es el client MCP.
1

📡 El protocolo MCP explicado

Imagínalo así: contratas a un asistente que habla 10 idiomas. Pero si cada proveedor inventa un idioma propio, el asistente tiene que aprender 10 gramáticas. MCP es el «idioma único» que todos los proveedores usan para comunicarse con agentes de IA.

MCP significa Model Context Protocol. Es un protocolo abierto, creado por Anthropic y liberado para toda la comunidad, que estandariza cómo los agentes de IA descubren y usan herramientas externas. Antes de MCP, cada herramienta tenía su propia integración. Ahora, un único protocolo conecta al agente con cualquiera servicio que implemente el patrón.

En la práctica, MCP usa JSON-RPC 2.0 sobre un canal de comunicación (normalmente stdio para procesos locales, o HTTP con SSE para servidores remotos). El agente envía un mensaje JSON que dice "quiero llamar a la herramienta X con estos parámetros" y el servidor responde con el resultado, también en JSON. Simple, predecible y extensible.

El cliente (Claude Code) envía una solicitud JSON-RPC; el servidor la ejecuta y devuelve el resultado.

En 1 frase: MCP es el JSON-RPC estandarizado que permite al agente llamar a cualquier herramienta externa con un único protocolo.

2

🏗️ Arquitectura cliente-servidor

Imagínalo así: un restaurante. El mesero (client) anota el pedido y lo lleva a la cocina (server). La cocina prepara el plato y lo devuelve. El mesero no necesita saber cocinar; la cocina no necesita saber servir. Cada uno hace su parte.

En el MCP, el client y Claude Code. Sabe cómo conversar con el usuario, planificar tareas y decidir cuándo necesita una herramienta. El server es un proceso independiente que sabe hacer algo específico: leer archivos, consultar una base de datos, enviar un correo electrónico. El cliente descubre qué ofrece el server (mediante tools/list), y después llama la herramienta que necesitas (vía tools/call).

El canal entre ellos puede ser stdio (el cliente inicia el servidor como proceso hijo y se comunica mediante stdin/stdout) o HTTP + SSE (el servidor se ejecuta de forma remota y acepta conexiones). En el día a día con Claude Code, casi siempre usas stdio: el agente inicia el proceso MCP, se comunica con él y lo termina al finalizar la sesión.

¿Quién es el «cliente» en el ecosistema MCP de Claude Code?

En 1 frase: Claude Code (client) inicia el MCP server, descubre las tools, llama a lo que necesita y termina.

3

📋 Descubrimiento de herramientas y esquemas

Cuando el cliente se conecta a un servidor MCP, lo primero que hace (después del handshake) es pedir la lista de herramientas disponibles mediante tools/list. Cada herramienta viene con tres cosas: un nombre (p. ej., read_query), una descripción (texto que explica lo que hace), y un inputSchema (JSON Schema que indica qué parámetros acepta).

El agente lee el schema y «entiende» qué parámetros debe proporcionar. Es como si cada tool viniera con un manual integrado. Cuanto mejores sean la descripción y el schema, más acierta el agente a la primera. Un schema deficiente es como darle un formulario sin etiquetas: el agente tendrá que adivinar.

exemplo-tool-schema.json 
{
  "name": "read_query",
  "description": "Execute a SELECT query against the database",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "The SQL SELECT query to execute"
      }
    },
    "required": ["query"]
  }
}

El esquema es el contrato

El inputSchema funciona exactamente como un JSON Schema de OpenAPI. Si ya trabajaste con APIs REST documentadas mediante Swagger/OpenAPI, el mecanismo es idéntico: el esquema describe tipos, campos obligatorios y descripciones. La diferencia es que quien lee el esquema no es un desarrollador humano, sino el propio agente de IA.

En 1 frase: cada tool tiene un schema JSON que el agente lee para saber exactamente qué enviar.

4

💡 Por qué importa MCP

Imagínalo así: antes del USB, cada dispositivo tenía un conector diferente. El USB estandarizó la conexión y el ecosistema de periféricos explotó. MCP es el "USB de los agentes de IA".

Sin MCP, Claude Code solo tiene las herramientas built-in: leer y escribir archivos, ejecutar bash, buscar en la web. Funciona, pero es como una computadora sin puertos USB: hace lo básico y nada más. Con MCP, conectas tantos «periféricos» como quieras: base de datos, Slack, email, calendario, cualquier API.

El impacto práctico es enorme. En vez de escribir scripts glue para cada integración, configuras un servidor MCP y el agente lo descubre por sí solo qué puede hacer. La estandarización significa que cualquier MCP server creado por cualquier persona funciona con cualquier MCP client. Composición sin límites.

Sin MCP

  • * Solo herramientas integradas (file, bash, web)
  • * Cada integración = script personalizado
  • * No escala: 5 integraciones = 5 scripts
  • * Agente limitado al filesystem

Con MCP

  • * Cientos de tools mediante un protocolo estándar
  • * Configuración única en settings.json
  • * Escala: 50 tools = el mismo patrón
  • * El agente opera bases de datos, APIs, SaaS, todo

En 1 frase: MCP transforma Claude Code de "editor de archivos" en "operador de sistemas conectado a todo".

🌍 Ecosistema actual

El ecosistema MCP ya es amplio. Hay más de 200 servidores open source que cubren categorías como: DevOps (Git, Docker, Kubernetes), Base de datos (Postgres, SQLite, Redis, MongoDB), SaaS (Slack, Notion, Linear, Gmail, Calendar), Nube (AWS, GCP, Cloudflare), y Utilidades (automatización del navegador, búsqueda web, conversión de archivos).

Los servidores oficiales de Anthropic cubren lo básico: filesystem, git, SQLite, Postgres, puppeteer, brave-search. La comunidad aporta el resto. Repositorios como awesome-mcp-servers en GitHub y es el marketplace Smithery.ai son los mejores puntos de partida para descubrir qué existe.

🔄 Analogía con las API REST

Si ya trabajaste con APIs REST, MCP te resultará familiar. En REST, tienes endpoints (GET /users, POST /orders). En MCP, tienes herramientas (list_users, create_order). En REST, la documentación viene en una especificación OpenAPI. En MCP, viene en el inputSchema.

La diferencia fundamental: REST se creó para que los desarrolladores humanos lo llamaran mediante código. MCP se creó para agentes de IA llamen automáticamente. Por eso el schema es más descriptivo (el agente necesita "entender" qué hace la tool con solo leer la descripción) y el discovery es automático (el agente enumera las tools en runtime, sin leer documentación).

AspectoREST APIMCP
UnidadEndpoint (URL + método)Tool (nombre + schema)
DocumentaciónOpenAPI / SwaggerinputSchema (JSON Schema)
DiscoveryManual (leer la documentación)Automático (tools/list)
ConsumidorCódigo escrito por una personaAgente de IA (automático)
TransporteHTTPstdio o HTTP+SSE

En 1 frase: MCP es como una API REST, pero con discovery automático y optimizado para agentes (no para humanos).
